# 项目讲解与追问准备

## 一句话版本

> Agent Crossbar 是一个本地 Agent 工作台：同一条 run 的 Spec、事件、评测和交付结论
> 都能在一台机器上复现；交付结论只有 block、fix、ship。

## 30 秒版本

> Coding Agent 生成代码后，团队要么全信，要么人工逐行读。我做了个本地闸门：
> 31 条确定性规则查密钥、注入和危险命令，关联 run 查 Token/时长/工具预算，
> 风险豁免必须有 owner 和到期时间，最后输出 block/fix/ship。
> 我用两个公开漏洞项目做独立基准，限定口径精确率 83.3%、召回率 71.4%。

## 2 分钟版本（按数据流讲）

1. **Spec**：Agent 定义不可变，落库前算 SHA-256。这样评测引用的版本不会漂。
2. **Run**：`run_service` 创建 run，运行时适配器循环执行；每个事件有单调序号。
3. **Trace**：事件规范化后落 SQLite WAL，同时通过 SSE 推给 UI；终态也落库。
4. **Eval**：评测为每个 case 真跑一次 run，断言既能看最终输出，也能看工具序列、
   调用次数和错误。
5. **Security gate**：扫描目录，命中规则后映射到策略条款；如果带 `run_id`，
   再读同一条 run 的事件算行为预算；豁免按 owner + 到期时间过滤；最后给结论。
6. **交付**：Markdown 贴 PR，SARIF 进 Code Scanning，阻断时 CLI 退出码 1。

## 8 分钟版本（加取舍）

- 为什么 SQLite：单操作员、本地、WAL 足够；不是多租户，不吹分布式。
- 为什么 sidecar 只绑回环 + 随机 token：桌面进程和 Python 进程分离，但攻击面要小。
- 为什么安全扫描默认不调模型：审计工具自己必须先证明不外发；模型复核是显式开关。
- 为什么保留确定性规则：结论可解释、可回归、可进 CI；LLM 适合补充，不适合当唯一闸门。
- 为什么结论只有三态：企业需要能执行的结论，不需要一个 87 分的“综合评分”。
- 为什么豁免要到期：永久忽略等于没有闸门。

## 高频追问

**Q：这不就是 Semgrep 吗？**
A：不是替代。它解决的是“代码 + Agent 行为 + 组织豁免”放在同一个交付结论里。
规则引擎可以替换成 Semgrep，但 run 预算和豁免流程是 Crossbar 自己的。

**Q：为什么召回只有 71.4%？**
A：因为只覆盖已支持规则族，DSVW 的 SQL 拼接和路径穿越没检出，我没藏。
这也说明它是交付闸门，不是完整 SAST。

**Q：整仓库精确率 16.7% 是不是很差？**
A：是。主要误报来自 vendor 压缩库、教程和测试脚本。限定应用代码是 83.3%。
下一步做默认忽略目录和规则级 allowlist，并公开下降曲线。

**Q：3 个真实用户呢？**
A：没完成。README 写的是未完成，没有编造。下一步只给他们 README 和 demo，
记录卡点再修。

**Q：你项目里最难的部分是什么？**
A：不是写规则，是让结论可追溯：同一条 run 的事件、评测断言、代码证据和豁免
必须能互相对上，而且任何一项缺失都不能假装通过。

**Q：如果重做，你会改什么？**
A：先做误报治理和真实用户，而不是继续加页面；规则引擎应该更早接 Semgrep/CodeQL，
把自研精力放在“行为预算 + 交付结论”这个差异点上。

**Q：为什么不做 OfferAgent 了？**
A：业务 Agent 的壁垒在数据和渠道，不在代码；Crossbar 的壁垒是工程证据链。
校招简历里一个能深挖的项目比三个讲不清的项目强。
