评审视角：大厂技术主管 / 校招终面面试官。  
原则：只看能被验证的东西；不把“我实现了”当成“它成立”。

## P0：不修就会被一句话打穿

### 1. 产品没有“结论”

有 run、trace、eval、compare，但没有回答“这次能不能交付”。
面试官会问：“所以你这个系统最后给出什么？”现在只能回答“能看到很多信息”。

**修法**：新增交付闸门（security review + behavior budget + verdict + waiver）。

### 2. 安全能力完全缺失，而这是当下最真实的需求

README 里没有任何安全/合规/外发边界。企业用 coding agent 的第一阻力就是：
密钥有没有带进去、危险代码有没有合进去、出了事能不能查。

**修法**：把 CodeSentinel 收进 Crossbar 作为一等能力，而不是外挂脚本。

### 3. 没有独立证据

RAG 基准的语料和查询是自己写的；安全样本也会是自己写的。
自己出题自己考，分数再高也不构成“检出率”。

**修法**：引入外部漏洞项目（如 DSVW）与真实仓库作为对照，公开难看的结果。

### 4. 真实用户为零

没有一个人在不看说明的情况下跑通过。所有“可用性”都是自评。

**修法**：用户试用包 + 3 人记录；做不到就如实写“未验证”，不要编。

## P1：会在深挖时暴露

### 5. 新机器 10 分钟跑不通
`verify.ps1` 依赖 `.venv`、`cargo`、`npm`，且是 PowerShell 专用。
缺 `make demo` / `docker` / 单命令引导。

### 6. 没有 CI
没有 GitHub Actions。所有“测试通过”都只在本机成立。
需要：Python + Node + Rust 三套检查；安全扫描作为独立 job。

### 7. 安全边界只写在文档里
README 说“本地优先”，但代码里没有统一的 egress 记录与拦截。
审计工具自己必须先证明不外发。

### 8. “Worker 池”容易被误读
实际是注册表 + 健康检查 + 轮转 + 失败转移，不是调度器/集群。
UI 叫“私有执行节点”会让人以为是分布式调度；需要在页面首屏写清边界。

### 9. 评测只覆盖单次结果
没有 flaky 检测、没有跨批次趋势、没有“接受风险”的流程。
企业不会因为一次 100% 就放行。

### 10. 并发与容量没有证据
SQLite 单写 + 单 sidecar 是合理的工作台设计，但没有压测数字。
不要说“高并发”，要说“单操作员、本地、可接受 N 个并发 run”。

### 11. 错误本地化靠字符串正则
新增错误码容易漏翻；缺“未翻译错误”的兜底与统计。

### 12. 样式集中在一个 76KB 文件
改动风险高；缺组件级边界。短期可接受，长期要拆。

### 13. 可访问性没有自动化
有 aria 标签，但没有 axe/键盘焦点测试；不能声称“无障碍达标”。

### 14. 成本口径需要写清
`cost_usd` 是 Decimal 字符串；聚合、比较、展示的口径要统一，否则数字会打架。

### 15. 迁移只前进
`schema_version` 升级失败没有回滚说明；本地数据损坏时缺恢复路径。

### 16. 依赖声明宽
`fastapi>=0.115` 这类宽约束在应用里可以，但要靠 `uv.lock` 固定；README 要写清“用 uv 同步”。

## P2：影响“顶尖感”，不影响正确性

- README 首屏没有截图/GIF，没有 3 分钟演示路径。
- 没有 LICENSE、SECURITY.md、CONTRIBUTING。
- “Crossbar” 这个名字需要解释；中文副标题仍偏工程。
- 测试数量多，但没有把“失败路径”的证据摆出来（provider 超时、MCP 断连、工具失败）。
- 没有安装包/签名的可复现说明。

---

## 本轮要补的四件事（按顺序）

1. **交付闸门**：安全扫描 + 合规条款 + 行为预算 + 结论 + 豁免。
2. **独立基准**：外部漏洞项目 + 真实仓库，公开召回与误报。
3. **CI + 一键演示**：GitHub Actions，SARIF 上传，`make demo`。
4. **试用与材料**：3 人试用包、3 分钟脚本、简历两版。

完成 1–3 后，综合评分预期 8.6；加上 3 个真实用户才能到 9.0。
